Checkout CD model

Checkout loops and graphs: a CD operating model

A future-state operating model for a 50-person functional team that handles checkout for multiple products in the enterprise. Loops are PDSA iterations that build quality in. The graph is the set of contracts with channel stakeholders, so every party who needs a clear outcome has a clear outcome.

After Hanako (@hanakoxbt), Loops and Graphs.

The article in one page

“A loop makes a unit of work correct without you. A graph decides which units exist at all.”

Loop: produce, check, correct, repeat until greenA PDSA cycle inside every value stream step. Study is a check a program can fail.

Step 1 · Splitter

Intake and slice

Current state

Wait / cycle time: fill in

Product lines send large projects into quarterly intake. Work is cut by component (front end, back end, QA), so slices wait on each other.

CD future state

Target cycle time: fill in

Product owner and squad cut work by outcome and blast radius into thin vertical slices: one issue, one bounded job, one input, one output. Only real dependencies become edges.

Copilot
Agent mode or Copilot Chat drafts a slice proposal and flags arrows with no shared data (no variable crosses, so no edge).
Human
Product owner approves the slice plan and assigns each slice a contract and a lane.
Lane
Sets the lane for each slice
Gate
  • GREEN every issue names its contract, lane and acceptance example
  • GREEN no slice is larger than one day
  • GREEN every dependency names the data that crosses

Step 2 · The check that can fail

Acceptance test first

Current state

Wait / cycle time: fill in

QA writes test cases after code is done. Acceptance is a manual regression pass near release, so the check arrives late and is easy to argue with.

CD future state

Target cycle time: fill in

A human trio (developer, product owner, stakeholder voice) writes the executable acceptance test before any code, Farley style, in the language of the contract. It is locked: the agent can run it, never edit it.

Copilot
May suggest extra edge cases in chat. It never commits to the `acceptance/` folder.
Human
Writes and commits the acceptance test. CODEOWNERS on `acceptance/` plus a ruleset requiring code-owner review keep it human-owned.
Lane
Human only, every lane
Gate
  • GREEN the new acceptance test exists and fails before any code
  • GREEN test lives under acceptance/ and is code-owner protected
  • NOT A CHECK "the story is clear"

Step 3 · Worker with a loop inside

Build

Current state

Wait / cycle time: fill in

Long-lived feature branches per project. Merges are big and risky, so people batch them, which makes them bigger.

CD future state

Target cycle time: fill in

The issue is assigned to Copilot coding agent. It works in its own environment, opens a draft pull request on a short-lived branch off trunk, and loops produce, check, correct until green. New behavior ships behind a feature flag.

Copilot
Coding agent writes code and unit tests and runs the locked acceptance test. Developers use agent mode in the IDE for slices that need pairing.
Human
None inside the loop. After three failed corrections the slice goes back to a human: the problem is in the plan, not the code.
Lane
Lanes 1 and 2 only; lane 3 is human-authored
Gate
  • GREEN acceptance suite exits 0
  • GREEN the diff touches only files listed in the plan
  • GREEN no file under acceptance/ changed

Step 4 · Code nodes

Verify

Current state

Wait / cycle time: fill in

A nightly build into a shared QA environment, then a manual regression cycle. Failures come back as a batch days later.

CD future state

Target cycle time: fill in

Every push runs deterministic checks with no model in them: build, unit, consumer-driven contract tests per stakeholder, mutation testing on changed code, CodeQL, dependency and secret scanning, card-data scope check.

Copilot
Receives the returned unit with verdict, reason, evidence and scope, and fixes only that unit.
Human
Platform group owns and improves the pipeline itself.
Lane
Same checks for all lanes
Gate
  • GREEN every stakeholder contract test passes
  • GREEN mutation score on changed code at or above team baseline
  • GREEN no new high security finding, no secrets
  • NOT A CHECK "no errors were raised"

Step 5 · Gate: the human approves the last step

Review and merge

Current state

Wait / cycle time: fill in

Two reviewers read every line, then a weekly change board. Humans sit in the middle of the graph and set its speed.

CD future state

Target cycle time: fill in

Copilot code review comments first and the agent resolves them. Then one accountable human approves the merge to trunk, reading evidence in order: deterministic results, the agent's session trajectory, rollback history of this area, and the model's own assessment last.

Copilot
Code review leaves comments; coding agent answers them with new commits.
Human
One approver merges to trunk. Set the ruleset so the person who assigned the agent is not the only approver.
Lane
Lane 1: approve merge. Lane 2: approve merge and ramp plan
Gate
  • GREEN all required checks pass
  • GREEN code-owner approval recorded
  • GREEN agent session log attached to the pull request

Step 6 · Lanes by blast radius

Release

Current state

Wait / cycle time: fill in

Monthly release windows, manual deploy steps, all-or-nothing rollouts across every product line at once.

CD future state

Target cycle time: fill in

Every merge deploys to production dark, behind a flag. Rollout ramps by product line (1, 10, 50, 100 percent) with automatic rollback when an SLO or contract signal breaks.

Copilot
None in lane 3. In lanes 1 and 2, the agent can open the flag-ramp change as a pull request.
Human
Lane 1 ramps automatically. Lane 2 needs an accountable flag ramp approval. Lane 3 never opens to agents.
Lane
All three lanes apply here
Gate
  • GREEN payment auth rate and error rate inside SLO for this cohort
  • GREEN no contract signal breached
  • GREEN rollback tested for this flag

Step 7 · Learning edge

Operate and learn

Current state

Wait / cycle time: fill in

Incidents are reviewed in a quarterly retro. Learnings go to a wiki page. Next quarter starts from the same place with the same blind spots.

CD future state

Target cycle time: fill in

Each accepted result or incident yields a derived constraint. It lands in the slicing brief, in `.github/copilot-instructions.md`, and as a new locked acceptance test, so the next run starts where this one ended.

Copilot
Drafts the derived constraint and the instruction-file change as a pull request.
Human
Squad accepts the constraint; stakeholders confirm their contract signal.
Lane
Constraint changes follow lane 1
Gate
  • ACCEPTED promo slice for product line B green on first pass
  • DERIVED price rounding happens only in the pricing service
  • LANDS IN slicing brief, copilot-instructions, acceptance/pricing

Lanes by blast radius

LaneCheckout examplesGateAgent autonomy
1. Reversible and containedCopy, UI behind a flag, a support view, a new testDeterministic checks, one human merge approvalCoding agent builds end to end
2. Reversible but wideShared pricing library, API schema addition, fraud call timeoutChecks plus trajectory review, staged ramp, accountable ramp approvalCoding agent builds; human approves merge and ramp
3. Hard to reversePayment capture and refund logic, ledger schema, data migrations, card-data scopeClosed to agents. Human-authored change, human decision before executionSuggestions in agent mode only

Lane 3 is not a high threshold. It is a lane that does not open, because thresholds get adjusted and closed lanes do not. Payment capture, refunds, the ledger, and card data stay off-limits to agents.

Return paths

Correction edge: return the unit, not the batch

UNIT      promo-code slice, product line B
VERDICT   red
REASON    acceptance/promo_stacking failed
EVIDENCE  expected total 84.00, got 80.00, pricing/discounts.ts:112
SCOPE     fix this file only, do not touch other slices
ATTEMPT   2 of 3

Four good slices stay merged. After three failed attempts the slice goes back to a human, because the plan is wrong.

Learning edge: a constraint, not the output

ACCEPTED   tax slice for new jurisdiction, green first pass
DERIVED    tax is computed only by the tax service, never in UI
LANDS IN   slicing brief
           .github/copilot-instructions.md
           acceptance/tax (new locked test)

Where to start

  1. Pick one repeated flow For example, onboarding a product line's promo rules. Draw the splitter, the lanes, the merge, one gate and one back edge.
  2. Build the gate first Locked acceptance tests and required checks. Everything gets easier once something can fail loudly.
  3. Then the lanes Label every issue lane 1, 2 or 3. Let Copilot coding agent take lane 1 issues end to end.
  4. Then the learning edge Once results are being accepted, turn each into a constraint in the brief and .github/copilot-instructions.md.
  5. Move the human to the last step Retire intermediate sign-offs; keep one accountable merge and ramp approval.
